# Technical Concerns, Observations, and Proposed Solutions

While drafting the ELI5 documentation for the Zegel format, several potential edge cases and security nuances were noted regarding the implementation as described in the `FORMAT_SPEC.md`. Following an extensive review of modern cryptographic literature, here are the detailed concerns and proposed solutions for future Zegel development.

## 1. Expiration Time Spoofing
The documentation mentions that expiration dates are checked against the current time (Step 8 of Verification: `If FLAG_HAS_EXPIRATION: check current time < expiration timestamp`).
*   **Concern:** If a user possesses the Master Key and the encrypted `.zgl` file, and the expiration validation relies solely on the host machine's local system clock, a malicious actor could simply change their OS system time to a date prior to the expiration timestamp to bypass the restriction.
*   **Proposed Solution (Hardware Enclaves / Online Renewal):** To truly enforce expiration against a host-level adversary, Zegel must integrate with Trusted Execution Environments (TEEs) like Intel SGX, Apple Secure Enclave, or ARM TrustZone. These environments possess monotonic counters and secure Real-Time Clocks (RTCs) that the OS cannot spoof. Alternatively, for high-security use cases, Zegel could implement a "license server" model where the extraction requires a brief online handshake to verify the current time via the Roughtime protocol before releasing the final key share.

## 2. Canary Trap Evasion (Re-encryption)
Canary Traps work by embedding a unique identifier (padding) into the ciphertext during the encryption process, which does not alter the Merkle root of the plaintext.
*   **Concern:** If a malicious recipient ("Bob") receives his unique, canary-trapped `.zgl` file and the Master Key, he can extract the raw plaintext. If Bob then *re-seals* that plaintext using his own instance of Zegel (generating a new `.zgl` file with a new salt, new IVs, new Master Key, and no canary padding), the leaked file will no longer contain the canary identifying him.
*   **Proposed Solution (Plaintext Steganography):** To survive decryption and re-encryption, the canary must be embedded in the *plaintext itself*, not just the cryptographic padding. Zegel could implement an optional module for text watermarking (e.g., using zero-width characters like U+200B, synonymous word substitution, or varying whitespace) or image steganography (embedding bits in image noise). This ensures the "trap" survives even if the raw data is extracted and re-sealed.

## 3. Redaction vs Original Hash Verification
When a block is redacted, its ciphertext is replaced with random bytes.
*   **Concern:** The `FORMAT_SPEC.md` mentions that applications can store the `original_hash` of the file in the metadata. If a file is redacted, the Merkle root remains valid (because the redacted block is skipped during decryption validation), but the overall hash of the extracted *plaintext* will no longer match the `original_hash` stored in the metadata. This creates confusion between "File Integrity" and "Content Integrity".
*   **Proposed Solution (Block-Level Manifest):** Instead of just storing one global `original_hash`, the metadata should optionally store a manifest of individual SHA-256 hashes for each *original* plaintext block. When a file is partially redacted and extracted, the reader can compute the hashes of the surviving blocks, match them against the manifest, and cryptographically prove that the *remaining* text is exactly as originally authored, while explicitly flagging which blocks were removed.

## 4. Selective Disclosure & File Context (The "Cut-off" Problem)
*   **Concern:** When using Selective Disclosure, providing only a subset of blocks (e.g., Block 8 and 9) might inadvertently leak context if the blocks cut off mid-sentence or mid-data structure. For example, if a JSON object spans blocks 7, 8, and 9, extracting only 8 and 9 might result in unparseable JSON or misleading text fragments.
*   **Proposed Solution (Content-Defined Chunking):** Instead of splitting files into rigid 64KB blocks, Zegel could implement Content-Defined Chunking (CDC) using algorithms like Rabin fingerprinting. CDC calculates block boundaries based on the actual content (e.g., naturally splitting blocks at the end of paragraphs, database rows, or JSON objects). This ensures that when a Selective Disclosure token is issued, the extracted data represents a complete, logical thought or data structure rather than a fractured string of bytes.
